# 已完成

- 找到第三方库` unwinding`
- 遇到的问题
  1. 直接使用这个库，运行时报错scause=0x2,fsd指令为非法指令。但是qemu在启动时开启了d和f扩展
  2. 将库纳入本地，形成一个crate，去掉保存现场时的fsd指令。safeos.elf文件的`.eh_frame`仅包括rust_main中的函数，unwinding库中函数无法在`.eh_frame`中找到对应的fde项，无法进行unwind。这里初步判断为缺失某些编译或链接选项
  3. 将unwinding纳入rust_main，成为其中的mod，并加入编译选项`-Cforce-unwind-tables`,并在Cargo.toml中设置`panic='unwind'`，可以成功在`.eh_frame`中找到unwinding代码所对应的fde项，并正确解析。
  4. 最新的问题：解析fde项，恢复寄存器值时。调用`wrapping_add`函数，该函数返回时ra被设置为kernel stack地址，导致系统崩溃。将该函数替换为正常+符号运算时仍有同样的错误。
- 总结：
  - 现在的问题都出现在unwinding最开始的步骤：恢复上一个函数调用点的现场。考虑自己实现一个通过解析fde来实现backtrace。如果backtrace可以正常跑，再去考虑unwind的逻辑。
  - unwindnig时大部分的工作都是指令集无关的，只有在恢复寄存器时不同指令集会有不同的寄存器以及存放顺序。考虑将theseus的指令集无关的unwind逻辑用于safeos。theseus并没有使用personality函数，而是自己实现了解析出lsda的函数，可能会比依靠personality函数进行跳转更为可靠与可控
  - 与unwinding库的作者交流中，主要探讨的问题是为何unwinding 作为一个单独crate时会丢失eh_frame信息
